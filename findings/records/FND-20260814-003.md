# FND-20260814-003 — Cancellation queue can lose an unprocessed or concurrent cancel request

## Verified improvement

A successful cancellation mutation now calls `_durable_push()` before cancellation ACK. Standalone push-before-ACK behavior is materially improved.

## Remaining concrete defect

The Worker cancellation queue is an array with **clear-all** ACK semantics:
- GET `/cancel_requests` returns the whole array;
- DELETE `/cancel_requests` writes the entire queue to `[]`.

The consumer loops all requests, but increments `cancelled` only for `ok` / `already_cancelled`. If at least one request succeeds, it performs one durable push and then clears the **entire** queue, including requests that were `not_found`, malformed, otherwise unresolved, or that arrived concurrently after the GET.

### Concrete mixed-run loss counterexample

1. Pending placement P is fetched and validated, but is not appended until Phase 3.
2. Cancellation C for P is already in `cancel_requests`.
3. `_process_cancel_requests()` runs during Phase 1, before P is appended; `cancel_bet(P)` returns `not_found`.
4. Another cancellation C2 in the same queue succeeds (`ok`).
5. Consumer durably pushes C2, then DELETE `/cancel_requests` clears the whole queue, losing C.
6. Phase 3 appends/pushes/ACKs P.
7. User's cancellation intent C is permanently lost.

There is also a concurrent-arrival race: a new cancel request queued between consumer GET and clear-all DELETE is erased without ever being processed.

The new mixed test at `a90be4c492b736b348dba9b3847c3b1d9823031a` does not detect this. It only asserts `>=2` push calls and `>=2` DELETE calls; it does not assert per-intent identity, ordering, partial failure, same-bet placement+cancel, or ACK-failure retry behavior.

## Required closure

Use a cancellation ACK model that cannot clear unrelated/unprocessed requests. Preferred target:
- stable cancel-request ID at enqueue;
- per-item ACK/delete (`DELETE /cancel_requests/{id}`) or an equivalently safe transactional mechanism;
- `not_found` that may correspond to a same-run pending placement remains RETRY, never dropped;
- concurrent new request after GET survives ACK of older requests;
- accepted placement + cancellation may share one durable mutation boundary if implemented safely;
- no placement or cancellation ACK before the exact corresponding durable state exists remotely;
- retry after either ACK failure is idempotent.

Add deterministic tests for same-bet placement+cancel, partial queue success, concurrent/new request preservation, push failure and ACK failure.
