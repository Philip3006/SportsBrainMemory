# FND-20260814-003 — Cancellation identity improved, but KV array read-modify-write is still race-unsafe

## Verified improvement

At `fd52d1b858dc08caae355de7ed9fab3a36ed47a9`:
- each newly queued cancellation gets a stable ID;
- consumer ACK uses `DELETE /cancel_requests/{id}`;
- unresolved/not-found requests remain queued;
- ACK retry is idempotent;
- the prior consumer clear-all ACK path is no longer used.

## Remaining concrete defects

### 0. Default-user cancel prefix overlaps every non-default user

At candidate head `5aeae738bcd357c1ee6b36f666fe6ebfb59396da`, `_cancelIntentPrefix(DEFAULT_USER)` returns `cancel_intent:` while non-default users use `cancel_intent:{user}:`.

Cloudflare KV prefix listing for the default user therefore also matches every non-default key such as `cancel_intent:bob:{id}`. This violates per-user queue isolation and can make the default-user consumer inspect another user's cancellation intent.

Required closure: namespace every user explicitly, including the default user, e.g. `cancel_intent:philip:{id}`. Add a deterministic Worker test proving default-user listing excludes another user's cancel intent.

## Previously identified defects now fixed on candidate head



### 1. Per-item endpoint is not actually concurrency-safe

`DELETE /cancel_requests/{id}` still implements:
1. read the entire cancellation array from KV;
2. filter one ID locally;
3. write the entire resulting array back.

A concurrent enqueue can therefore still be lost:

1. delete request reads `[A, B]`;
2. concurrent enqueue reads/writes `[A, B, C]`;
3. delete writes stale filtered array `[B]`;
4. newly queued `C` disappears without processing.

Stable IDs alone do not make whole-array KV read-modify-write atomic.

### 2. Unsafe clear-all API remains exposed

Authenticated `DELETE /cancel_requests` still writes the entire queue to `[]`. Even though the Python consumer no longer calls it, the queue boundary still exposes a bypass that can erase unproven cancellation intents.

## Required closure

Use a storage/ACK model where deleting one cancellation cannot overwrite another concurrent cancellation. Preferred minimal target:
- store each cancel intent as its own KV key keyed by stable cancel ID, or use another truly atomic/transactional primitive;
- GET may aggregate individual keys for the consumer;
- DELETE by ID deletes only that key;
- disable/remove clear-all DELETE from the normal API (or make it impossible to use as a normal ACK path).

If Cloudflare KV listing semantics make individual-key storage impractical, use an equally safe transactional store; do not simulate per-item semantics with whole-array read-modify-write.

Add deterministic Worker tests proving a newly/concurrently added request survives deletion of an older ID and that clear-all normal DELETE is rejected/absent.
